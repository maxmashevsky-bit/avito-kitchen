# API-контракты MVP

Авторитетные машиночитаемые контракты находятся в:

- `api/kitchen.openapi.yaml` — Public API, Partner API и operational endpoints платформы;
- `api/restaurant.openapi.yaml` — Integration API и operational endpoints demo-ресторана.

Обе спецификации используют OpenAPI 3.1.0 и содержат параметры, заголовки, тела, ответы,
бизнес-ошибки и примеры каждого метода.

## Контуры доступа

| Контур | Идентификация | Назначение |
| --- | --- | --- |
| Public catalog | Нет | Список заведений, карточка и опубликованное меню |
| Public orders | Обязательный `X-User-ID` | Создание и чтение только своих заказов; заголовок не является защитой |
| Partner API | `Authorization: Bearer <partner-key>` | Публикация меню, просмотр и изменение заказов заведения |
| Restaurant Integration API | `Authorization: Bearer <integration-key>` | Доставка заказов worker-ом и восстановление после потерянного ответа |
| `/healthz`, `/readyz` | Нет | Docker healthcheck и диагностика готовности зависимостей |

Partner key хранится на платформе только в виде хеша. Integration key передаётся процессам через
environment variables и не фиксируется в Git. Чужие пользовательские и партнёрские ресурсы
маскируются как `404 NOT_FOUND`.

## Основные HTTP-решения

- Все деньги — положительные `int64` в полях `*_minor`; валюта — только `RUB`.
- Время передаётся в RFC 3339/`date-time` и хранится в UTC.
- Внутренние ID — UUID. `external_item_id` уникален только в контексте заведения.
- JSON-объекты запрещают неизвестные поля через `additionalProperties: false`.
- Списки заведений и заказов используют непрозрачный cursor, `limit` по умолчанию 20 и максимум 100.
- Каждая ошибка и каждый ответ содержат корреляционный `X-Request-ID`; тело ошибки повторяет его
  в `request_id`.
- В `details` разрешены только безопасные структурированные данные, полезные клиенту; stack trace,
  SQL и внутренние секреты не возвращаются.

Коды HTTP разделены следующим образом:

| HTTP | Смысл |
| --- | --- |
| `400` | Невалидный JSON, заголовок, параметр или структурно неверное тело |
| `401` | Неверный Partner/Integration Bearer key |
| `404` | Ресурс отсутствует или скрыт от текущего участника |
| `409` | Конфликт с текущей ценой, наличием, версией, статусом или idempotency record |
| `413` | Превышен лимит тела; машинный код остаётся `VALIDATION_ERROR` |
| `422` | Позиции синтаксически валидного заказа принадлежат разным заведениям |
| `500` | Неожиданная внутренняя ошибка |
| `503` | Readiness-зависимость временно недоступна |

## Идемпотентность заказов

### Создание пользовательского заказа

`POST /api/v1/orders` требует `Idempotency-Key`. Значимые поля запроса канонизируются и
хешируются: позиции сортируются по `menu_item_id`, их порядок несущественен, а дубли ID запрещены.
Пара `(X-User-ID, Idempotency-Key)` уникальна:

- первый успех — `201 Created`, `Idempotency-Replayed: false`;
- тот же ключ и эквивалентное тело — `200 OK`, прежний заказ,
  `Idempotency-Replayed: true`;
- тот же ключ и другое тело — `409 IDEMPOTENCY_KEY_REUSED`.

### Получение заказа demo-рестораном

`platform_order_id` выполняет роль идемпотентного ключа. При расчёте payload hash позиции также
сортируются по идентификатору, а дубли запрещены:

- первый устойчиво сохранённый результат — `201 Created`;
- идентичная повторная доставка — `200 OK` с прежним решением;
- тот же ID и иной payload — `409 PLATFORM_ORDER_ID_REUSED`.

Недостаток фактического остатка не является HTTP-ошибкой: restaurant API успешно сохраняет заказ
со статусом `rejected` и причиной `ITEM_UNAVAILABLE`. Это позволяет отличить бизнес-решение от
временной технической ошибки, которую worker должен повторить.

## Версия меню

Полная публикация `PUT /partner/v1/menu` содержит целочисленную `version`:

- новая версия должна быть больше текущей;
- точный повтор той же версии и содержимого возвращает прежний `200`;
- старая версия или то же число с другим содержимым дают `409 STALE_MENU_VERSION`.

Точечный `PATCH` передаёт `expected_version`. Она должна равняться текущей версии, после чего
платформа атомарно увеличивает версию на один. Таким образом, отдельный `If-Match` в MVP не нужен.

## Покрытие методов

`kitchen.openapi.yaml` описывает семь публичных, пять партнёрских и два operational endpoint-а.
`restaurant.openapi.yaml` описывает два интеграционных и два operational endpoint-а. Дополнительные
operational endpoints платформы — единственное расширение исходного минимального списка; они нужны
для обязательных Docker healthcheck-ов и уже зафиксированы в ADR-014.

## Кодогенерация

Для генерации используется `github.com/oapi-codegen/oapi-codegen/v2` версии `v2.8.0`. Инструмент
закреплён в `go.mod`, его настройки лежат рядом со спецификациями, а результат — в
`internal/generated`. Команда `make generate` повторяет генерацию локально; сгенерированные файлы
не редактируются вручную.
