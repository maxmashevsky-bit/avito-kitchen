# Первоначальные архитектурные решения

Решения ниже приняты для MVP и должны быть понятны на интервью. Они не делают систему
production-ready заранее. Существенные изменения добавляются сюда с контекстом, альтернативами и
последствиями.

## ADR-001. Модульный монолит и отдельный demo-ресторан

**Статус:** принято.

Основная платформа реализуется одним Go-модулем с доменными модулями каталога, заказов, партнёров
и outbox. `kitchen-api` и `kitchen-worker` — разные процессы над общей кодовой базой.
`restaurant-demo` — отдельный процесс и интеграционная граница.

Так проще проследить бизнес-транзакции и запустить задание, чем набор микросервисов, но API и
worker можно независимо масштабировать. Demo-ресторан остаётся действительно внешней системой.

## ADR-002. Раздельное владение данными

**Статус:** принято.

Платформа и demo-ресторан используют отдельные PostgreSQL 17. Платформа владеет каталогом,
опубликованной копией меню, заказами, историей и outbox; ресторан — реальным меню, остатками,
входящими заказами и резервами. Между базами нет внешних ключей и прямых SQL-запросов.

Раздельное владение не позволяет незаметно связать сервисы общей схемой и делает интеграционные
ошибки видимыми. Цена — eventual consistency копии меню и необходимость идемпотентного обмена.

## ADR-003. Зафиксированный Go/PostgreSQL стек

**Статус:** принято.

Используются Go 1.27, `net/http`, `chi/v5`, PostgreSQL 17, `pgx/v5`/`pgxpool`, ручной SQL и
`goose/v3`. HTTP-контракты — OpenAPI 3.1 с `oapi-codegen/v2`. Для кодогенератора выбран
`v2.8.0` — зафиксированный релиз с поддержкой OpenAPI 3.1 и требованием Go 1.25+, которое
удовлетворяется Go 1.27. Инструменты и библиотеки получают закреплённые версии; `goose` и
`oapi-codegen` подключаются как project tools в `go.mod` на Этапе 6.

Стек мал, прозрачен и позволяет обсуждать SQL и HTTP без скрытой магии ORM или фреймворка.

## ADR-004. REST-контракты проектируются до обработчиков

**Статус:** принято.

Публичный, Partner и интеграционный контуры сначала описываются в OpenAPI. Из спецификации
воспроизводимо генерируются серверные типы/интерфейсы; generated-код не правится вручную.
Все ошибки используют `code`, `message`, необязательный `details` и `request_id`.

Это уменьшает расхождение реализации и документации. Совместимость OpenAPI с кодогенератором
проверяется до написания основной HTTP-логики.

## ADR-005. Внутренние UUID и scoped external IDs

**Статус:** принято.

Основные сущности получают внутренние UUID. Идентификаторы из системы заведения хранятся
отдельно и уникальны только совместно с `restaurant_id`. `platform_order_id` уникален в базе
demo-ресторана.

Так совпадающие ID разных партнёров не конфликтуют, а смена внешней системы не ломает связи
платформы.

## ADR-006. Упрощённая идентификация пользователя и Partner API key

**Статус:** принято для MVP.

Публичный API получает непрозрачный `X-User-ID` и всегда ограничивает им доступ к заказам.
Это заглушка, не механизм безопасности. Partner API использует Bearer key; хранится только
криптографический хеш ключа, сравниваемый безопасным способом. Ключи поступают из окружения/seed.

Полноценный identity provider и жизненный цикл ключей находятся вне MVP, но границы замены явно
видны в HTTP middleware и конфигурации.

## ADR-007. Целочисленные деньги и снимки заказа

**Статус:** принято.

Денежные значения хранятся целым числом копеек и сопровождаются валютой `RUB`; `float` не
используется. Сервер сверяет увиденную клиентом цену и рассчитывает итог. В позициях заказа
сохраняются имя, цена и внешний ID на момент оформления.

Старые заказы не меняются вместе с меню, округление однозначно, а тихое повышение цены исключено.

## ADR-008. Версионированная опубликованная копия меню

**Статус:** принято.

Полная публикация меню атомарно создаёт/заменяет опубликованную версию платформы и передаёт
`version` в теле. Точный повтор версии и содержимого идемпотентен, а старая версия или повторное
число с другим содержимым получают `STALE_MENU_VERSION`. Точечное обновление передаёт
`expected_version`; при совпадении платформа атомарно увеличивает версию на один. Отдельный
`If-Match` для MVP не используется.

Платформа быстро обслуживает чтения, но не претендует на окончательную истинность остатков:
ресторан повторно проверяет и резервирует их при получении заказа.

## ADR-009. Строгий линейный жизненный цикл заказа

**Статус:** принято.

Переходы: `pending_confirmation` → `accepted|rejected|cancelled`, затем `accepted` → `preparing`
→ `ready` → `delivering` → `delivered`. Терминальные статусы неизменны. Пользовательская отмена
разрешена из `pending_confirmation`, только пока outbox-событие ещё не захвачено для передачи.
Отмена, запись истории и исключение события из доставки выполняются атомарно; гонку с worker-ом
закрывает условное обновление/блокировка в БД.

Линейная модель достаточно выразительна для demo, не требует курьерского домена и легко
проверяется централизованной доменной функцией. Расширение возвратами или частичной отменой
потребует отдельного решения.

## ADR-010. Идемпотентное создание заказа

**Статус:** принято.

`POST /api/v1/orders` требует `Idempotency-Key`. БД гарантирует уникальность пары
`(user_id, idempotency_key)`. Вместе с заказом сохраняется детерминированный request hash значимых
полей после нормализации. Совпадающий hash возвращает существующий заказ, отличный — HTTP 409 с
`IDEMPOTENCY_KEY_REUSED`.

Ограничение БД закрывает конкурентные запросы; одной предварительной проверки приложением было бы
недостаточно. Алгоритм канонизации будет зафиксирован тестами до реализации репозитория.

## ADR-011. Transactional outbox и at-least-once

**Статус:** принято.

Заказ и outbox-событие создаются одной транзакцией. Worker выбирает доступные строки небольшими
пачками через `FOR UPDATE SKIP LOCKED`, делает HTTP-вызов с timeout и повторяет временные ошибки
с ограниченным exponential backoff. Исчерпанные события сохраняют попытки и последнюю ошибку.
Demo-ресторан идемпотентен по `platform_order_id` и резервирует строки с блокировкой.

Модель обеспечивает at-least-once, а не exactly-once. Потеря ответа приводит к безопасному
повтору, а не к повторному списанию.

## ADR-012. PostgreSQL вместо дополнительных инфраструктурных компонентов

**Статус:** принято для MVP.

- **Kafka/RabbitMQ не нужны:** один тип события и один интеграционный получатель обслуживаются
  надёжным outbox в уже обязательной БД. Брокер рассматривается, если появятся минимум три
  независимых потребителя/нужен replay либо при нагрузочном тесте backlog устойчиво нарушает
  целевой p95 доставки 5 секунд после настройки batching и параллельных worker-ов.
- **Redis не нужен:** каталог и заказы читаются из индексированной PostgreSQL, распределённые
  сессии отсутствуют. Кэш рассматривается, если после оптимизации SQL p95 чтения каталога выше
  200 мс или CPU основной БД выше 70% не менее 15 минут на ожидаемом пике и измерения показывают,
  что повторные чтения действительно кэшируемы.
- **Kubernetes не нужен:** Compose достаточен для локального MVP. Оркестратор рассматривается при
  эксплуатации на нескольких узлах, требовании автоматического масштабирования/самовосстановления
  и нескольких репликах процессов, которыми Compose уже нельзя надёжно управлять.

Численные пороги — первоначальные критерии обсуждения, а не обещанный production SLO; перед
масштабированием их следует уточнить реальными нагрузочными измерениями.

## ADR-013. Реляционная модель и управляемые статусы

**Статус:** принято.

Связи, фильтруемые поля и деньги хранятся типизированными колонками. Статусы — `TEXT` с `CHECK`,
чтобы добавлять значения обычной миграцией без особенностей PostgreSQL enum. `JSONB` применяется
только для версионированного payload outbox и обоснованных снимков.

Целостность обеспечивается и доменными проверками, и PK/FK/UNIQUE/CHECK в БД.

## ADR-014. Наблюдаемость и безопасная конфигурация без отдельного стека

**Статус:** принято.

Процессы пишут структурированные JSON-логи через `log/slog`, передают/создают `request_id` и
добавляют `order_id`/`restaurant_id` по контексту. Предусматриваются `/healthz` и `/readyz`,
graceful shutdown, тайм-ауты и лимиты тела. Конфигурация задаётся окружением с валидацией при
старте; `.env.example` содержит только безопасные значения.

Prometheus, tracing backend и централизованный log storage не добавляются в локальный MVP.

## ADR-015. Проверки по слоям и реальные PostgreSQL integration-тесты

**Статус:** принято.

Чистые бизнес-правила покрываются table-driven unit-тестами, HTTP — `httptest`, а SQL,
ограничения и конкуренция — Testcontainers for Go с PostgreSQL 17. Сквозной shell/Go-сценарий
работает поверх Docker Compose. CI запускает генерацию/проверку актуальности, тесты, race detector,
`go vet`, `golangci-lint` v2, `govulncheck` и проверку Compose.

Интеграционные тесты могут пропускаться только с явным сообщением, если Docker недоступен; в CI
Docker обязателен.

## ADR-016. Диаграммы как код и локальная генерация

**Статус:** принято.

CJM, C4, ER, sequence и state diagram хранятся как PlantUML рядом со сгенерированными SVG.
C4 использует локально закреплённые includes/совместимый локальный шаблон, поэтому генерация не
зависит от сети. `make diagrams` воспроизводит результат.

## ADR-017. HTTP-семантика и cursor-pagination

**Статус:** принято.

Public order API использует `X-User-ID` как обязательную, но небезопасную заглушку. Partner API и
Integration API demo-ресторана используют разные Bearer keys. Это не добавляет пользовательскую
аутентификацию, но не оставляет межсервисный endpoint открытым.

Первичное создание заказа возвращает `201`, идемпотентный повтор — `200` и
`Idempotency-Replayed: true`, конфликт payload — `409`. Недостаток остатка demo-ресторана является
успешно сохранённым бизнес-решением `rejected`, а не HTTP-ошибкой. Списки используют cursor вместо
offset: это сохраняет стабильность при конкурентном добавлении данных и соответствует будущим
индексам заказов по `(created_at, id)` и заведений по `(name, id)`.

Структурные ошибки получают `400`, отсутствие доступа — `401`, скрытый/отсутствующий ресурс —
`404`, конфликт состояния — `409`, слишком большое тело — `413`, нарушение правила одного
заведения — `422`, внутренняя ошибка — `500`, неготовность зависимости — `503`. Тело всегда имеет
единый envelope `code`, `message`, опциональный `details`, `request_id`.

## ADR-018. Demo credentials, bootstrap и исторические ссылки

**Статус:** принято для MVP.

Partner key в Kitchen DB хранится только как SHA-256. Demo использует отдельный integration key
из environment; его локальное значение явно помечено как учебное. При более чем одном
внешнем партнёре понадобятся per-partner credentials в secret manager и ротация.

Demo-заведение и его остатки создаются seed-миграциями; `restaurant-demo` после старта
публикует актуальную копию меню со следующей версией. Это bootstrap для воспроизводимого
E2E, а не общий production-механизм синхронизации.

`menu_item_id` в позиции старого заказа и external item ID во входящей позиции ресторана
являются snapshot-ссылками, а не FK. Это позволяет удалять пропавшие из новой публикации
позиции, не ломая неизменяемую историю. Исходная целостность проверяется в транзакции
создания и затем фиксируется полным снимком.
