# Требования к MVP «Авито.Кухня»

## 1. Назначение и источники

Сервис предоставляет API будущему web-клиенту и закрытый API заведениям, позволяя найти
заведение, посмотреть его опубликованное меню, оформить заказ и проследить его состояние.
Отдельный demo-сервис одного ресторана показывает реальный интеграционный контур.

Авторитетным источником бизнес-задания служит
`backend-trainee-assignment-autumn-2026.md`. Этот документ конкретизирует его с учётом
согласованных ограничений реализации. При расхождении приоритет имеет исходное условие.

## 2. Участники и границы ответственности

- **Пользователь** без полноценной авторизации просматривает каталог и управляет своими заказами.
- **Web-клиент** в MVP не реализуется; он хранит корзину и обращается к публичному API.
- **Заведение** публикует меню, получает заказы, принимает или отклоняет их и обновляет статусы.
- **Основная платформа** владеет каталогом заведений, копией меню, заказами, историей статусов,
  связями с внешними идентификаторами и событиями outbox.
- **Demo-ресторан** владеет фактическим меню, остатками, входящими заказами и резервами.

Запускаемая топология состоит из `kitchen-api`, `kitchen-worker`, `restaurant-demo`,
`kitchen-postgres` и `restaurant-postgres`; одноразовые процессы миграции допустимы. API и worker
используют общий Go-модуль, но запускаются разными командами.

## 3. Обязательные результаты

- Публичный API для каталога, меню и заказов.
- Закрытый Partner API для меню и жизненного цикла заказов.
- Интеграционный API и отдельная база demo-ресторана.
- Основной API, worker, demo-ресторан и обе PostgreSQL запускаются через Docker Compose.
- Версионируемые SQL-миграции обеих баз.
- OpenAPI 3.1 спецификации основного и интеграционного API с примерами и единой моделью ошибок.
- Code-generated диаграммы: два CJM, C4 Container, ER, sequence создания заказа и state заказа;
  в репозитории хранятся исходники PlantUML и сгенерированные SVG.
- README с запуском, демонстрацией, архитектурой, данными, API, надёжностью, тестированием,
  упрощениями и возможными направлениями масштабирования.
- Зафиксированные линтер, статический анализ, тесты и GitHub Actions.
- Воспроизводимые команды сборки, генерации, проверок и запуска в `Makefile`.

## 4. Пользовательские сценарии

### 4.1. Поиск и выбор

1. Пользователь получает список доступных заведений.
2. Открывает карточку выбранного заведения.
3. Получает только опубликованное платформой меню с ценами и копией доступности.
4. Добавляет позиции одного заведения в корзину web-клиента.

### 4.2. Оформление заказа

1. Клиент передаёт `X-User-ID`, обязательный `Idempotency-Key`, позиции, количества и цены,
   которые видел пользователь.
2. Платформа проверяет формат запроса, одно заведение, состояние заведения, наличие позиций,
   копию доступности и актуальность цен.
3. Платформа сама рассчитывает итог в копейках; присланный клиентом итог не считается доверенным.
4. В одной транзакции создаются заказ `pending_confirmation`, снимки позиций, начальная история
   статуса и outbox-событие для ресторана.
5. Повтор эквивалентного запроса с тем же ключом возвращает ранее созданный заказ.
6. Worker доставляет заказ ресторану, а окончательное наличие подтверждает ресторан.

### 4.3. Просмотр и отмена

1. Пользователь получает список только своих заказов и открывает отдельный заказ.
2. Пользователь может отменить заказ только в `pending_confirmation` и до начала его передачи
   ресторану; при отмене ожидающее outbox-событие атомарно исключается из доставки.
3. Отмена конкурирует с захватом события worker-ом и решением ресторана атомарно: побеждает
   первое допустимое действие; проигравший запрос получает бизнес-ошибку, а актуальное состояние
   не изменяется.

## 5. Сценарии заведения

### 5.1. Публикация меню

1. Предварительно зарегистрированное заведение вызывает Partner API с Bearer API-ключом.
2. Заведение целиком публикует новую версию меню либо обновляет отдельную позицию.
3. Платформа связывает внешние идентификаторы с внутренними UUID только в пределах заведения.
4. Устаревшая версия изменения не перезаписывает более новое меню.

### 5.2. Обработка заказа

1. Demo-ресторан идемпотентно принимает заказ по `platform_order_id`.
2. В транзакции он блокирует нужные строки остатков и проверяет все позиции.
3. При достаточном остатке ресторан создаёт входящий заказ, единожды резервирует товар и сохраняет
   решение о принятии; при недостатке сохраняет решение об отклонении без частичного резерва.
4. Ответ интеграционного API содержит сохранённое решение, которое платформа применяет к заказу.
5. Повторная доставка возвращает прежнее решение и не меняет остатки повторно.
6. Заведение видит свои заказы в Partner API; endpoint решения поддерживает явное принятие или
   отклонение для партнёрского сценария и подчиняется той же машине состояний.
7. Для принятого заказа заведение последовательно выставляет `preparing`, `ready`,
   `delivering` и `delivered`.

## 6. Бизнес-правила

### 6.1. Идентификация и доступ

- Внутренние идентификаторы сущностей — UUID; внешний ID не заменяет внутренний.
- Внешний ID позиции уникален в пределах заведения, но может повторяться у другого заведения.
- Пользователь определяется временным заголовком `X-User-ID`; это не защита и не авторизация.
- Запросы пользователя отфильтровываются по `user_id`, чтобы не возвращать чужие заказы.
- Partner API принимает `Authorization: Bearer <key>`; в основной БД хранится только хеш ключа.
- Интеграционные секреты задаются окружением и никогда не фиксируются в Git.

### 6.2. Меню и деньги

- Платформа хранит опубликованную копию меню, а ресторан остаётся источником истины по остаткам.
- Цена — положительное целое число копеек; единственная валюта MVP — `RUB`; `float` запрещён.
- Количество каждой позиции — положительное целое число.
- Клиентская цена каждой позиции сверяется с актуальной. При расхождении заказ не создаётся.
- Недоступная или отсутствующая позиция не может быть молча удалена или заменена.
- Версия меню монотонно растёт; конкурентное устаревшее обновление отклоняется.

### 6.3. Заказ и идемпотентность

- Один заказ содержит позиции ровно одного заведения.
- Корзина не хранится в backend; оформление получает выбранные позиции целиком.
- Название и цена позиции копируются в `order_items`, поэтому прошлые заказы неизменны при
  последующей публикации меню.
- Уникальность `(user_id, idempotency_key)` гарантируется также ограничением БД.
- Для идемпотентности хранится детерминированный отпечаток значимых полей запроса.
- Тот же ключ и тот же отпечаток возвращают существующий результат; тот же ключ и иное тело
  дают `IDEMPOTENCY_KEY_REUSED` и HTTP 409.
- Пустой ключ, пустой заказ, дубли позиций и неположительное количество отклоняются валидацией.

### 6.4. Статусы и переходы

Разрешены только следующие переходы:

- `pending_confirmation` → `accepted`, `rejected`, `cancelled`;
- `accepted` → `preparing`;
- `preparing` → `ready`;
- `ready` → `delivering`;
- `delivering` → `delivered`.

`delivered`, `rejected` и `cancelled` терминальны. Переход в тот же статус и пропуск промежуточных
статусов считаются недопустимыми. Каждый успешный переход добавляет запись истории в той же
транзакции. Время хранится как `timestamptz` и интерпретируется в UTC.

Пользовательская отмена разрешена только до захвата outbox-события worker-ом. Это исключает
ситуацию, когда ресторан уже зарезервировал остаток, а платформа успела отменить ещё ожидающий
заказ без отдельного протокола освобождения резерва.

### 6.5. Надёжность интеграции

- Заказ, позиции, начальная история и outbox-событие фиксируются атомарно.
- Worker забирает доступные события через `FOR UPDATE SKIP LOCKED`.
- Доставка — at-least-once; exactly-once не заявляется.
- Временные ошибки повторяются с ограниченным exponential backoff и HTTP timeout.
- После лимита попыток событие остаётся в БД с диагностическими данными и не теряется.
- `platform_order_id` уникален в demo-ресторане; резервирование повторно не выполняется.
- Потеря ответа безопасна: повтор интеграционного запроса возвращает сохранённое решение.

## 7. Ошибочные сценарии

Все API-ошибки имеют стабильный `code`, понятный `message`, опциональный `details` и `request_id`.
Конкретное соответствие HTTP-кодам фиксируется в OpenAPI на Этапе 4.

- `ITEM_UNAVAILABLE` — позиции нет, она снята с публикации или копия доступности отрицательна.
- `PRICE_CHANGED` — клиент видел другую цену; ответ сообщает затронутые позиции и актуальные цены.
- `MULTIPLE_RESTAURANTS` — позиции принадлежат разным заведениям.
- `RESTAURANT_CLOSED` — заведение не принимает новые заказы.
- `IDEMPOTENCY_KEY_REUSED` — ключ уже связан с иным телом запроса.
- `INVALID_STATUS_TRANSITION` — источник или текущее состояние не допускают переход.
- `STALE_MENU_VERSION` — изменение основано на устаревшей версии меню.
- `ORDER_NOT_CANCELLABLE` — передача ресторану уже началась либо статус более не допускает отмену.
- `VALIDATION_ERROR` — некорректные заголовки, поля, количества или пустой заказ.
- `UNAUTHORIZED` — Partner или Integration API key отсутствует либо неверен.
- `PLATFORM_ORDER_ID_REUSED` — demo-ресторан получил прежний ID заказа с другим payload.
- `NOT_FOUND` — сущность отсутствует либо недоступна текущему участнику.
- `SERVICE_UNAVAILABLE` — обязательная зависимость не прошла readiness-проверку.
- `INTERNAL_ERROR` — неожиданная внутренняя ошибка без раскрытия деталей реализации.

Дополнительно должны быть корректно обработаны: неверный Partner API-ключ, слишком большое тело,
невалидный JSON, тайм-аут demo-ресторана, повторная доставка, исчерпание retry, конкурентное
резервирование последней единицы и гонка отмены с решением ресторана.

## 8. Минимальный API-контур

Публичный API:

- `GET /api/v1/restaurants`;
- `GET /api/v1/restaurants/{restaurantId}`;
- `GET /api/v1/restaurants/{restaurantId}/menu`;
- `POST /api/v1/orders`;
- `GET /api/v1/orders`;
- `GET /api/v1/orders/{orderId}`;
- `POST /api/v1/orders/{orderId}/cancel`.

Partner API:

- `PUT /partner/v1/menu`;
- `PATCH /partner/v1/menu/items/{externalItemId}`;
- `GET /partner/v1/orders`;
- `POST /partner/v1/orders/{orderId}/decision`;
- `PATCH /partner/v1/orders/{orderId}/status`.

Интеграционный API demo-ресторана:

- `POST /integration/v1/orders`;
- `GET /integration/v1/orders/{platformOrderId}`;
- `GET /healthz`;
- `GET /readyz`.

Расширять этот контур можно только под явно описанный бизнес-сценарий. Формальные схемы полей,
заголовков, ответов, кодов и примеров будут зафиксированы в OpenAPI на Этапе 4.

## 9. Данные и запросы

Основная БД содержит `restaurants`, `restaurant_integrations`, `menus`, `menu_items`, `orders`,
`order_items`, `order_status_history`, `outbox_events`. БД demo-ресторана содержит `items`,
`incoming_orders`, `incoming_order_items`.

Схема должна включать PK/FK, `CHECK`, уникальные ограничения и индексы под реальные запросы:

- внешний ID в пределах заведения;
- `(user_id, idempotency_key)`;
- история заказов пользователя;
- заказы заведения по статусу;
- частичный индекс доступных необработанных outbox-событий.

Статусы хранятся как `TEXT` с `CHECK`, а не PostgreSQL enum. `JSONB` допустим для payload outbox
и обоснованных снимков, но не вместо реляционных полей, используемых в связях и поиске.

## 10. Нефункциональные требования

- Go 1.27, идиоматичный код, небольшие функции и явная обработка ошибок.
- `net/http`, `chi/v5`, `pgx/v5`/`pgxpool`, ручной параметризованный SQL, `goose/v3`.
- `context.Context` во всех I/O, тайм-ауты серверов и клиентов, лимит тела, graceful shutdown.
- Настроенный пул соединений и отсутствие глобального изменяемого состояния.
- JSON-логи `slog` с `request_id` и, где применимо, `order_id`/`restaurant_id`.
- Конфигурация через environment variables; безопасный `.env.example`; секретов в Git нет.
- OpenAPI 3.1 и воспроизводимый `oapi-codegen/v2`; generated-код вручную не изменяется.
- Закреплённые версии зависимостей, `goose` и `oapi-codegen` как project tools в `go.mod`.
- Unit-, PostgreSQL integration- и E2E-тесты, `go vet`, race detector, `golangci-lint` v2,
  `govulncheck` и GitHub Actions.

## 11. Границы MVP

В MVP входят каталог заведений, опубликованное меню, оформление/просмотр/отмена заказа,
обработка заведением, demo-интеграция, надёжная доставка заказа и требуемая документация.

Не входят: пользовательский frontend, полноценная пользовательская аутентификация и
авторизация, оплата, курьерская подсистема, сложная геолокация, рекомендации, полнотекстовый поиск,
уведомления, промокоды, корзина на сервере и административная панель. Без отдельного согласования
не используются Kafka, Redis, RabbitMQ, Kubernetes, Nginx, MongoDB, Elasticsearch, gRPC и GORM.

## 12. Осознанные упрощения

- `X-User-ID` заменяет identity provider только для демонстрации API.
- RUB — единственная валюта; налоги, скидки, чаевые и стоимость доставки не рассчитываются.
- Карточки заведений и интеграционные ключи предварительно создаются seed/миграцией;
  self-service onboarding не реализуется.
- Платформа хранит лишь копию доступности; окончательное резервирование делает ресторан.
- Demo-ресторан принимает автоматическое устойчивое решение по остаткам, а дальнейшие статусы
  меняются через Partner API; реальная кассовая/кухонная система не моделируется.
- Поиск заведений — простой список без ранжирования, георадиуса и полнотекстового движка.
- Retry выполняет worker на PostgreSQL outbox; отдельный брокер и кэш для масштаба MVP не нужны.
- Доставка представлена статусами без маршрутизации и управления курьерами.

## 13. Критерии успешности

- `docker compose up --build` поднимает всю систему, healthcheck-и становятся успешными.
- Миграции применяются автоматически либо одной документированной командой.
- Demo-сценарий проходит от публикации меню до принятого заказа и нового статуса.
- Повтор с тем же idempotency key не создаёт дубль, а недоступный товар корректно отклоняется.
- OpenAPI соответствует публичному поведению обработчиков; кодогенерация актуальна.
- Все исходники диаграмм воспроизводимо генерируют SVG.
- `go test ./...`, `go test -race ./...`, `go vet ./...`, `golangci-lint run` проходят.
- Integration-тесты подтверждают транзакционность, ограничения, конкурентный резерв и
  параллельный `SKIP LOCKED`; E2E-сценарий воспроизводим.
- `govulncheck ./...` не находит используемых известных уязвимостей либо исключение объяснено.
- `docker compose config` проходит; секретов и случайных артефактов в Git нет.
- README позволяет новому проверяющему запустить проект и понять решения без устных пояснений.
